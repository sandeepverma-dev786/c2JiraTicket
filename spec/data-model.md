# Support Ticket Management System Data Model

This document defines the logical persistence/domain model using only decisions established in [requirements.md](requirements.md), [state-machine.md](state-machine.md), and [architecture.md](architecture.md). It does not define Java classes or implementation code.

## Types

| Type | Values |
| --- | --- |
| `TicketStatus` | `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED`, `CANCELLED` |
| `Priority` | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |

The valid status transitions and initial status are defined in [state-machine.md](state-machine.md). New tickets start in `OPEN`.

## Ticket

| Field | Logical type | Required? | Constraints and ownership |
| --- | --- | --- | --- |
| `id` | UUID | Yes | Generated by the server. Clients do not provide it. |
| `title` | String | Yes | 1-200 characters. |
| `description` | String | Yes | 1-2000 characters. |
| `priority` | `Priority` | Yes | One of the defined `Priority` values. |
| `status` | `TicketStatus` | Yes | Server-controlled; new tickets start in `OPEN`, and changes must follow the approved state machine. |
| `assignee` | String | No | Optional; not a reference to a User entity. |
| `createdAt` | Timestamp | Yes | Generated by the server when the ticket is created. Clients do not provide it. |
| `updatedAt` | Timestamp | Yes | Generated and maintained by the server. Clients do not provide it. |

## Comment

| Field | Logical type | Required? | Constraints and ownership |
| --- | --- | --- | --- |
| `id` | UUID | Yes | Generated by the server. Clients do not provide it. |
| `ticketId` | UUID / Ticket relationship | Yes | References exactly one existing Ticket. |
| `author` | String | Yes | Supplied by the client. No further validation constraint is specified. |
| `content` | String | Yes | 1-1000 characters. |
| `createdAt` | Timestamp | Yes | Generated by the server when the comment is created. Clients do not provide it. |

## Relationship

- One Ticket has many Comments.
- Each Comment belongs to exactly one Ticket and stores the relationship through `ticketId` or an equivalent persistence relationship.
- Ticket deletion is out of scope. No delete or cascade behavior is required.
- Comment editing and deletion are out of scope.

## Validation and Generated Values

The backend is authoritative for validation. Enforce the required fields and character limits shown above; do not infer additional constraints such as assignee or author length limits. `priority` must be one of the defined enum values. `status` must be changed only according to the approved state machine.

The server generates entity identifiers as UUIDs and generates timestamps. Clients are not required to send IDs, `createdAt`, or `updatedAt` values. The client supplies the comment `author` as a String.

## Persistence and API Boundaries

- Persist Ticket and Comment data in file-based H2 for local development so it survives application restarts; in-memory-only H2 does not satisfy this requirement.
- Keep persistence access behind the repository/data-access layer.
- Persistence entities represent stored data and relationships. API request and response DTOs represent the REST contract and are separate models; do not expose persistence entities directly as API responses.
- Request DTOs must not require clients to provide server-generated IDs or timestamps. Response DTOs may represent the corresponding persisted values.
- Physical table and column names, database-specific UUID representation, and concrete timestamp serialization are not defined by the approved domain requirements.

## Open Questions

No domain-level model decisions remain unresolved in the approved requirements. Physical schema details and concrete timestamp representation are implementation choices, not additional domain requirements.
